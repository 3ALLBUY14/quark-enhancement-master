## 0. 结论摘要

**功能覆盖度属于同领域天花板，不存在大面积「功能漏做」；真正的缺口集中在三处：可靠性/可恢复性、兼容性与可维护性、文档与支持。**

- 功能面：约 27 个功能域，桌面 + 移动双端，还配了独立浏览器扩展，**没有明显漏掉的同类产品标配功能**。
- 结构性问题：
  1. **3.82 MB 单文件、无构建、无测试、无 CI** —— 直接后果是「升级即坏」的回归（v5.1.0 就修过一次「升级后目录文件无法显示」，而 issue #20 正是同一症状）。
  2. **批量操作无撤销、无审计、无事务、无同名冲突策略** —— 这是唯一会**造成用户数据损失**的一类缺口，优先级最高。
  3. **对官方接口变动无熔断/降级** —— 官方抽风时表现为「文件列表全空 + 无限重试」，用户无法区分是自己网络问题还是脚本坏了。
- 待办真实存在但不多：README 里作者已亲口承认 4 处能力缺口，open issue 2 条（1 条还是已修未关）。

## 4. 待办事项

待办可从三个来源推导，全部有据可查：

### 4.1 挂起中的 issue（2 条 open）

| # | 标题 | 性质 | 备注 |

| 17 | 核显设备 GPU 占用过高（DOM 注入期） | 性能缺陷（有完整根因分析） | 报告者已定位到具体 CSS：`.pk-gv-media-mount` 的 `transform: translateZ(0)` + `will-change: transform`、`#pk-audio-mini` / `.pk-img-ov` 的 `backdrop-filter: blur()`；建议加 **Lite 模式**开关；自 2026-09-07 挂起，v5.1.0 只做了「缓解」未根治 |
| 20 | 升级后盘内文件无法显示 | 回归缺陷 | 作者 2026-09-27 回复「已在 V5.1.0 修复」后**未关闭 issue**，issue 卫生问题 |

> 补充：v5.1.0 更新日志写的是「优化文件列表与网格视图渲染性能，缓解低配置设备的 GPU / CPU 占用及滚动微卡顿」——**「缓解」而非「修复」**，说明 #17 仍是开放项。

### 4.2 README 中作者亲口承认的能力缺口（4 处）

1. **视频首帧/切清晰度失败无法区分** —— 原文：「这个错误无法稳定区分是『官方资源还在准备中』还是『当前清晰度真的不可播放』……**如果后续能找到官方更可靠的状态字段，再继续优化这类误报问题**」。→ 明确的技术待办，指向依赖官方字段。
2. **分享提取次数上限的自动拦截不可靠** —— 原文：「仅在网页保持开启且设备未休眠时生效」。→ 本质是浏览器端方案的固有上限，无法根治。
3. **批量解压受官方并发/频率限制** —— 只能提示「系统繁忙，稍后重试」。
4. **容量不足时官方静默拦截** —— 粘贴后文件不出现，脚本无法预判，只能事后让用户自己查空间。

### 4.3 从 v5.x 迭代方向反推的隐性待办

v5.1.0 / v5.2.0 / v5.3.0 连续三个版本的更新日志主线是：**性能、稳定性、网络异常恢复、配置同步冲突处理**（如 5.3.0 的「区分首次加载失败与真实空目录、超时重试、网络异常重试、在线恢复重试、缓存列表保护」）。

→ 说明作者自己已把重心从「加功能」转向「修可靠性」。**功能已饱和，可靠性是当前主线。**

## 5. 遗漏与未覆盖场景

分三类，按危害排序。

### A. 可靠性 / 可恢复性（唯一会造成**数据损失**的一类，优先级最高）

| # | 缺口 | 场景后果 | 现状证据 |
|---|---|---|---|
| A1 | **批量重命名无撤销** | 规则填错，几千个文件名被改乱，只能靠记忆或导出过的清单手工改回 | 重命名为直接落盘 API 调用；仅查重有「不自动删」的保护，重命名没有 |
| A2 | **无操作审计日志** | 出了事无从追溯「谁在什么时候改了哪 3000 个文件」 | 全仓库无操作日志模块 |
| A3 | **无事务 / 无失败回滚** | 批量移动 1000 项，第 600 项失败，前 599 项已生效且无记录 | 只有「失败清单导出」，无回滚动作 |
| A4 | **无同名冲突策略** | 粘贴/转存到已有同名文件的目录，行为未文档化（覆盖？改名？跳过？）—— 批量操作的致命场景 | README 与 FAQ 均未提及同名处理语义 |
| A5 | **无容量预检** | 官方静默拦截，用户以为脚本坏了（FAQ 已印证这是高频困惑） | README 只教你「自己去查空间」 |
| A6 | **无并发修改检测** | 多端同时改同一批文件 → 状态错乱 | README 仅一句「不建议在其他客户端同时修改」，脚本层无锁、无版本校验 |
| A7 | **聚合视图删除后无法还原目录结构** | 在查重/透视/最近添加里批量删除 → 回收站还原时被堆到一个目录 | 作者在 FAQ 中承认是官方机制限制，但脚本**也未做任何防护**（如删除前记录原父目录） |
| A8 | **无回收站临期预警** | 15 天自动清空，临期文件无提示 | 回收站模块只展示剩余天数 |
| A9 | **云配置无版本快照** | 「冲突以云端为准」= 本地新改动会被静默覆盖，无回滚 | 5.2.0 明确定义了该语义 |

### B. 兼容性 / 可维护性（决定项目还能活多久）

| # | 缺口 | 现状 |
|---|---|---|
| B1 | **无构建与模块化** | 3.82 MB 单文件、82,239 行，无 `src/`、无打包脚本。外包改不动、自己改也易误伤 |
| B2 | **零自动化测试 + 零 CI** | 无 `.github/workflows`、无测试目录。772 次提交全靠手工回归，**v5.1.0 的回归修复正是缺测试的直接代价** |
| B3 | **API 端点未外置** | 路径/字段散落在 8 万行里，官方一改版要全文搜。无「改一处即生效」的适配层 |
| B4 | **无熔断/降级** | 官方异常时无限重试（#20 日志里 `Retry 1/5 … Retry 2/5` + `ERR_CONNECTION_CLOSED`），表现为「列表全空」，用户无法区分官方故障与脚本故障 |
| B5 | **无一键自检** | 用户报障只能贴控制台（#20 就是如此），维护成本高 |
| B6 | **无版本兼容矩阵** | 不记录「本版脚本验证过的官网版本/浏览器」，升级即坏无法预判 |
| B7 | **浏览器支持不明** | README 只建议 Edge/Chrome 最新版；Firefox 靠用户自测（#17 就是 Firefox 报告）；Safari / iOS 完全未声明 |
| B8 | **移动端功能覆盖未声明** | README 明确移动端只有 VLC + Gopeed，但**云归档、数据迁移、批量解压、分享次数上限在移动端是否可用，全文未提** —— 用户只能试 |

### C. 产品与体验（补全性质）

| # | 缺口 | 说明 |
|---|---|---|
| C1 | 无「空间占用排行」 | 有用量面板和文件透视，但没有「谁占了我的空间 Top 100」的直达视图 |
| C2 | 无目录快照 diff | 能导出目录树，但不能把两次导出做比对 → 发现不了文件被误删/被替换 |
| C3 | 无跨账号查重 | 支持多账号迁移，但查重只在当前账号内 |
| C4 | 伴生扩展 i18n 覆盖不明 | 主脚本 7 语，扩展只有单个 `i18n.js`，未确认是否同覆盖 |

## 6. 明确结论

1. **功能层面：不存在实质遗漏。** 27 个功能域覆盖了网盘增强类工具的标配与大量长尾（磁链内部文件树 + 部分保存、视频截帧 16 帧、在线字幕搜索、反代直链模板、多账号加密迁移、伴生扩展），在同类项目里属于功能最全的一档。**不要再往「加功能」方向提需求。**
2. **真正的遗漏是工程与安全网，不是功能。** 具体就是第 5 节 A 类 9 项 + B 类 8 项：无撤销、无审计、无事务、无冲突策略、无容量预检、无测试、无 CI、无熔断、无兼容矩阵。其中 **A1/A3/A4 是会真实造成用户文件混乱的缺陷**，而非体验瑕疵。
3. **项目当前的主要矛盾**：作者已在 5.1–5.3 连续三个版本投入性能与稳定性修补，但缺测试与 CI 导致「修一个坏一个」的回归反复出现（#20 vs 5.1.0 修复声明、#17 只「缓解」未修复）。**投入方向是对的，缺少的是安全网。**
4. **对维护者的一句话建议**：**先停止加功能，做两件事——把 API 端点集中成一张表，给核心链路加一个冒烟测试 + CI。** 这两件事的投入产出比远高于再做一个功能域。
